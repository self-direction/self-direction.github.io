Self-Direction · implementation

How the loop is built

Self-Direction is a thin layer around an ordinary agent. The snippets below are trimmed from our implementation to show the moving parts: they are meant to be read, not run. Every component is a standard tool, and the whole loop needs no extra teacher model and never updates the base weights. You can ask your AI agent to reference this and to replicate it.

  • vLLM inference server
  • SQLite failure memory
  • sentence-transformers router
  • PEFT LoRA adapters
  • Transformers trainer

01 · Overview

The whole loop, in one function

Every task first runs on the unchanged base model. Only after a verified failure does the loop store the failure, look for a stored skill that matches, train a new one if none does, and retry with the selected adapter. If that retry still fails, a final clean-base attempt is the fallback. The adapter is unloaded afterwards, so the next task starts from the base model again.

02 · Components

Five standard pieces

Each step of the loop maps onto a familiar tool. Inference runs on vLLM, failures live in SQLite, a small sentence-embedding model routes tasks to skills, the base model writes its own training data, and PEFT trains and loads rank-16 LoRA adapters while the base weights stay frozen.

2.1Inference

Attempt the task on vLLM

The agent is a plain ReAct loop over an OpenAI-compatible vLLM server: it calls tools until it produces a final answer or runs out of steps or tool calls. A benchmark verifier scores the answer. A failure is classified as a wrong answer, a missing final answer, an exhausted step or tool budget, or a crash.

2.2Storage

Remember the failure in SQLite

Each failure is one row: the task, the failure reason and the full trajectory, plus an open/resolved status. A de-duplication key makes writes idempotent, so a preempted job can resume without double-counting. Adapters live on disk next to a small JSON registry that records where each one came from.

2.3Routing

Choose one: reuse or train

Every stored adapter keeps the text of the task that produced it. A new failure is embedded with all-MiniLM-L6-v2 and compared with those tasks by cosine similarity. If the best match clears the threshold τ, the loop reuses that adapter and skips reflection and training entirely. With τ = 1 an adapter is only ever reused on its own task.

2.4Self-reflection

The same model writes its own lesson

The clean base model, with no adapter loaded, reads the failed task, the failure reason, the verifier's answer and its own trajectory. It writes up to 24 instruction → response examples that teach the missing procedure: which tools to call, how to read their output, and when to stop. It is told never to copy the answer, so the examples teach the process rather than the solution. No stronger teacher model is involved.

2.5Training

Distill the lesson into a LoRA adapter

The examples train a rank-16 LoRA adapter with PEFT. The failure reason picks the layers: budget and missing-answer failures adapt the attention projections, which steer planning, while wrong answers adapt the MLP down-projection. Matrix A is set from the top singular vectors of the frozen weight and kept frozen, and B starts at zero, so the adapter begins as a no-op and only B is trained, about 0.02% of the model's parameters. Training takes roughly 1.5 minutes on one H200, and the adapter takes about 85 MB on disk.

2.6Retry

Retry with the skill, then fall back

The selected adapter is loaded onto the frozen base model and the task is retried. With vLLM, adapters can be hot-loaded into the running server and selected per request by name, so serving many skills needs no restart. If the adapter-guided retry fails, the adapter is unloaded and one final attempt runs on the clean base model with a prompt noting that a prior attempt failed.

Our experiments apply adapters in-process with PEFT (load_adapter / set_adapter); the vLLM calls shown here are the equivalent serving path.
